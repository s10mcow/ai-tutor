# Ticket 08 verification and extension contract

## Delivered behavior

An owned activity accepts one still workbook or paper-art picture. The picture stays beside the question and conversation. The Learner sees the Tutor's interpretation, explicitly edits or confirms it, then asks for coaching in the same activity. Confirmation alone makes no provider call. Until confirmation, both the browser and action route block coaching; removing the picture restores typed input. An unreadable interpretation leaves an empty description and invites a clearer picture or the Learner's own description. Failed interpretation retains the attachment with a deliberate retry and an explanation of allowance holds.

Confirmed picture descriptions are observations, not Learner-authored evidence. They populate the current question and enter the normal ordered Tutor context as `confirmedPictures`. They never become provider instructions, tool definitions, or a Portfolio attempt. Art remains an art discussion; a maths connection is optional. Ordinary upload is visibly separate from a Portfolio save.

## Upload, authorization and lifetime

`POST /api/learners/:learnerId/session/:sessionId/images/:imageId` accepts raw raster bytes and `X-Picture-Kind: workbook|art`. It requires same-origin mutation and authenticated family/Learner/session ownership. No client URL, storage path, response MIME type or provider file ID is accepted. A client-generated opaque ID plus the original-byte hash makes unchanged upload replay safe. A different image requires explicit removal first.

The streaming request limit is 5,000,000 bytes, even without an honest Content-Length. Only JPEG/PNG/WebP signatures reach Sharp; actual format, single-frame status, decoded pixel limits and a complete decode are checked. Input is limited to 16 million pixels and 8,000 pixels per dimension. Normalization applies orientation, strips metadata, flattens transparency onto white, resizes within 2,000 × 2,000 and emits JPEG (maximum 3,000,000 bytes). Unsupported, truncated, animated and oversized pictures receive a recoverable error. Sharp 0.35.5 is pinned as a direct server dependency; its installed API documentation supplied the decoding/metadata contract.

- `GET .../images/:imageId` serves the normalized JPEG only after ownership and live-activity checks, with private/no-store, fixed MIME/disposition, nosniff and restrictive CSP headers. It never exposes a public asset URL.
- `PATCH .../images/:imageId` accepts `{operation:"interpret"}` or `{operation:"confirm",description}` (1–2,000 trimmed characters). Pending/completed interpretation replay does not dispatch again; failed retries receive a new private attempt ID. Confirmation updates the owned activity atomically.
- `DELETE .../images/:imageId` deliberately removes the temporary bytes. The already-confirmed question/ordinary conversation remains current activity context until activity end/expiry.
- `LearningSession.images` exposes metadata and confirmation state, never bytes, hashes or private provider attempt IDs. `SessionPicture` aborts pending browser requests on unmount and Learner switching.

Migration `08-session-images.sql` stores bounded bytea in PostgreSQL with a cascading foreign key to the owned learning session and one image per session. Web-process restart preserves the current attachment. End activity deletes its session and cascades its picture/actions. Logical expiry applies to direct asset access, confirmation and session operations; session access and the existing `sessions:purge` command physically delete expired rows through the same cascade. No filesystem is used as deployed storage. Browser tests establish access denial after end/expiry; the foreign key supplies the physical row deletion mechanism. Hosted idle cleanup scheduling, PostgreSQL/backup retention and absence of content in infrastructure logs remain ticket 14 activation checks; HTTP inaccessibility alone is not proof of deployed physical deletion.

## Image provider and allowance policy

`solResponse` is the common single-dispatch Responses adapter for text and inline image interpretation. Image understanding uses `gpt-6.1-sol`, Standard/default tier, foreground, `store:false`, `tools:[]`, disabled truncation, 2,000 maximum output tokens, explicit caching with no breakpoints, no SDK/network retries and no provider Files/Conversations state. Image text is untrusted subject matter, including apparent instructions in a workbook. The raw image is sent inline only for interpretation; later coaching receives the confirmed description in user data.

The `image` operation uses the versioned `sol-image-standard-no-cache-2026-11-16` policy through `meteredOperation`. It reserves the same proven full 922,000-token input ceiling plus bounded output at long-context rates: **3,718,000,000 nano-USD ($3.718)**. The 4,100,000-byte image-request ceiling is an app limit, never a token estimate. Returned authoritative Sol usage uses the existing category validation and measured-cost arithmetic, including invisible reasoning; invalid/missing usage or ambiguous network outcomes retain the conservative hold. No guessed image multiplier, token-count preflight, zero-cost image placeholder, unmetered fetch or hidden fallback was added.

`providerConfiguration(kind)` checks the selected operation before reservation and again while locking the common allowance. Image dispatch requires the existing account/project/funding/ZDR/application-retention evidence **and** `TUTOR_RETENTION_EVIDENCE.responsesImagesApproved: true`. That operator evidence must cover the actual Responses image feature, inline inputs and provider image-safety exceptions; text approval or `store:false` alone does not establish it. `GET /api/model-access?operation=image` is a read-only view of this operation's readiness. Image failures show that reason where available. Text readiness continues to use the existing default operation. No actual approval, credentials, provider request or paid activation was established.

## Contract for ticket 11

`lib/image-contract.ts` owns browser-safe metadata; `lib/session-images.ts` owns bounded decoding and owned temporary assets. `ownedImage` resolves family + intended Learner + live activity + image ID and returns normalized bytes server-side. A lasting Portfolio save must explicitly select the image, revalidate and lock the live owned source during its transaction, copy/retain the selected bytes under independent durable Portfolio ownership, and preserve replay identity. It must survive source deletion and a new web process. Do not turn the current session URL or Tutor interpretation into durable authority or the Learner's own explanation. This ticket intentionally adds no implicit Portfolio image save.
