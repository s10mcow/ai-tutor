# Ticket 09 verification and speech contract

## Delivered behavior

In a coaching activity, **Record a message** requests the microphone on a supported computer browser. **Stop and transcribe** ends capture; a hard sample limit and a wall-clock stop bound recording to 60 seconds. **Review your transcription** is editable. **Use this text** puts the accepted words into the existing composer, where the Learner chooses the message purpose and submits normally. Neither recording nor transcription starts a Tutor action. Typing and accepted speech therefore share the existing problem, activity, notes, fresh-challenge context and ordered exchange. Scratchpad, picture confirmation and intentional Portfolio saves keep their separate meanings.

**Read latest reply aloud** uses Web Speech synthesis only with an explicitly assigned English voice whose `localService` is exactly `true`. There is no default/null voice, remote voice, speech recognition API, `/audio/speech` endpoint or substitute Tutor model. This output is on-device and adds no provider charge. An absent/changed voice list or playback failure leaves readable text and an explanation. Capture stops current playback. Playback and capture are canceled on leaving/switching/ending/pausing; hidden tabs stop capture. Microphone permission arriving after cancellation has its tracks stopped. Aborted requests and unmounted controls cannot populate a different workspace.

## Recording and authorized HTTP boundary

`apps/web/app/_components/audio-capture.ts` exports `startAudioCapture(signal, onLimit)`, returning a one-shot `{ stop(): Blob, cancel(): void }`. It uses a real MediaStream, AudioContext and AudioWorklet. `stop` returns a canonical mono, 16-bit little-endian PCM WAV at 16 kHz. `cancel` discards chunks and stops tracks/context. Both release device resources. The contract performs no upload or storage; ticket 12 can reuse capture for an explicit Portfolio save without turning ordinary coaching into saved recordings.

`POST /api/learners/:learnerId/session/:sessionId/transcription` accepts raw `audio/wav` with a bounded `X-Recording-Id`. It authenticates the family, checks the intended Learner and current owned activity, requires same origin and rejects game/paused sessions. A streaming reader enforces a 1,920,044-byte ceiling before buffering further. The validator checks the exact RIFF/fmt/data layout, declared lengths, PCM format, sample rate, byte rate, channel count, alignment and actual sample length. Only 0.25–60 seconds is accepted. Unknown chunks, metadata, compressed formats, MIME-only disguises, arbitrary URLs and filenames are excluded.

A deterministic opaque attempt identity binds the recording ID to the authenticated family/Learner/session. The common SQL reservation prevents duplicate dispatch, including across restart. Transcription results are not cached for replay: repeating an already submitted ID returns a service/retry explanation without another call. A fresh recording is an explicit new operation. The route rechecks session existence, expiry, `breakRevision`, paused state and current profile before returning text. An intervening pause remains detectable after resume. UI abort does not imply cancellation of provider billing; the server finishes accounting without making a new learning action.

Ordinary audio exists only in browser/server request memory. There is no audio table, disk write, provider Files upload, object storage, public recording URL, or GET/download operation. The endpoint returns only bounded text. Unreviewed text is not written to session actions, notes or Portfolio. Only the subsequently submitted accepted text has the existing activity's fixed expiry. Billing records contain opaque operation/request IDs, status and numeric duration/cost metadata, never audio or words. Generic error logging does not include request/response bodies. Hosting request/body tracing, retention and backups still require pilot verification; source-level omission is not proof of hosted deletion.

## Supported provider and metering

The input adapter sends a completed in-memory multipart WAV to the fixed OpenAI `/v1/audio/transcriptions` endpoint with `model: "gpt-transcribe"` and JSON response format. No streaming, prompt, names, context, automatic retries or old speech model is used. The only transport override is the existing development-only loopback fictional provider. Credentials and organization/project headers remain server-owned.

The published rate is $0.0045 per minute. The versioned `gpt-transcribe-duration-2026-11-17` policy reserves a whole minute ($0.0045, 4,500,000 nano-USD) for every validated recording of no more than 60 seconds. This covers both proportional and whole-minute charging for the accepted duration. A valid response with `usage.type: "duration"` and finite positive `seconds <= 60` within one second of the independently validated sample duration is accounted at 75,000 nano-USD per second, rounding the larger of reported and validated duration upward to a whole second. This is deliberately conservative application accounting, not a claim to reproduce fractional invoice rounding. Missing usage, incompatible token usage, impossible duration, HTTP error, disconnect or timeout keeps the entire minute held as unresolved. Returned words never establish zero cost. Actual schema/usage and billing reconciliation remain part of pilot verification.

Speech uses the same funding window lock, shared allowance, unknown-outcome liability and parent **Model access** totals as text and images. `/api/model-access?operation=transcription` checks its smaller reservation and its endpoint retention evidence. Live access additionally requires `transcriptionsApproved: true` in the existing project-matched `TUTOR_RETENTION_EVIDENCE`; text approval alone cannot approve audio. No additional manual billing flag is introduced. `store:false` is not sent to the Audio API and is not represented as ZDR approval. Under-13 processing remains closed until actual approved project/endpoint retention and funding evidence are established.

Primary sources checked November 17, 2026 UTC: [file transcription guide](https://developers.openai.com/api/docs/guides/speech-to-text), [transcription request/response schema](https://developers.openai.com/api/reference/resources/audio/subresources/transcriptions/methods/create), [pricing](https://developers.openai.com/api/docs/pricing), [retention controls](https://developers.openai.com/api/docs/guides/your-data), and [Web Speech localService contract](https://webaudio.github.io/web-speech-api/). The transcription schema permits optional duration usage; the guide's minimal example omits it. The adapter therefore treats missing usage conservatively. Older file-transcription and TTS endpoints were not adopted.

## Verification and device limits

The agreed Playwright seam uses real browser components, Better Auth, application HTTP and isolated PostgreSQL. The only controlled boundaries are OpenAI HTTP and the microphone/speech-synthesizer device. The microphone fixture generates a fictional oscillator MediaStream; real AudioContext/AudioWorklet sample capture and WAV encoding remain exercised. Chromium's built-in fake microphone left `getUserMedia` pending on this Mac, so it was replaced at the hardware boundary, not by a fake app/audio encoder. No real microphone recording, child data or chargeable request was used. Synthesizer fixtures prove explicit local-voice selection and queue/cancel/error behavior; they do not prove that a real device produced audible sound.

Red-to-green slices observed missing record controls, microphone continuing after tab hiding, playback continuing during capture, and transcription accepted while paused. Scenarios cover reviewed/corrected speech, typed follow-up context, local read-aloud, microphone denial, service/playback failures, no remote fallback, hidden-tab track cleanup, profile/end cancellation, invalid/oversize/mismatched recordings, authentication/origin, durable duplicate protection, no unreviewed activity/Portfolio save, unknown usage and exhausted/retention-gated speech. Pause/resume checks use the shared persistent revision.

Supported computers need HTTPS (localhost for development), microphone permission, Web Audio with a 16-kHz context and AudioWorklet, plus an installed English local synthesis voice for read-aloud. A computer lacking that voice still supports typed interaction and approved input transcription, with clear output unavailability. Hardware microphone usability, audible output/quality on the actual laptops, recognition accuracy and live endpoint suitability remain explicit pilot checks.
