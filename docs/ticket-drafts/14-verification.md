# Ticket 14 verification and remaining pilot gates

## Implemented application behavior

The authenticated readiness response now includes text, image interpretation, transcription and research status from the same `modelAccess` policy used for operation admission, alongside the shared allowance. The parent panel shows each operation and hosted retention controls. Complete family setup requires all four operations to be live-ready; local controlled fixtures remain fictional even when available. Text-only approval can support a permitted synthetic text evaluation, but cannot establish complete family readiness. There is no browser approval toggle.

Every live operation additionally requires `TUTOR_APPLICATION_RETENTION_EVIDENCE`: observed native hourly cleanup, audited telemetry controls, the verified/disclosed recovery history window and a documented safe restore procedure. Current cleanup credentials must remain configured. The exact schema and evidence meaning are in [the operator runbook](../pilot-operations.md). No new recurring approval timer is introduced. Existing grant, funding-evidence and provider-approval expirations still apply.

Migration `14-pilot-readiness.sql` adds a single deployment establishment timestamp, set only after all operation gates are live-ready. It grants no access. Later allowance/account/retention interruptions show **Family AI paused** and preserve saved access; removing credentials cannot relabel established real work as fictional. Before establishment the authenticated UI remains a **Fictional-data preview**. Signed-out pages show **Private family space** and instruct the parent to check readiness before entering personal information.

The native hourly cleanup definition is top-level in `vercel.ts` under `withEve`. `/api/cron/purge-sessions` requires the independently configured `CRON_SECRET`, never a family session, request user-agent or platform bypass. Missing and incorrect authorization return 401 before any query. Successful deletion returns only aggregate `deletedSessions`; repeated calls are harmless. Database failure returns a content-free 503. It does not close the shared PostgreSQL pool or log error objects. Existing one-off `npm run sessions:purge` remains available for recovery.

The older integrated journey exposed a usability defect: a confirmed workbook question was visible and **Share attempt** enabled, but the server rejected the first attempt with “Start with a question.” Initial coaching now accepts an attempt when the server already owns a confirmed problem; a completely empty activity still requires its initial question/research claim. The journey verifies the corrected interpretation reaches coaching and the fresh challenge stays distinct.

README and environment documentation now describe all delivered features, production composition, operation gates and retention limits. The [synthetic evaluation cases](../evaluations/14-private-pilot.md) and prior reasoning rubric remain explicitly **unrun**. The runbook provides concrete same-window account-block recovery while preserving charges and unknown reservations, plus restore safeguards that prevent old ledger counters from recreating spent allowance.
