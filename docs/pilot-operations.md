## Hourly cleanup and retention

Root `vercel.ts` declares one native cron, `/api/cron/purge-sessions`, at minute 50 of every UTC hour. It is top-level configuration passed through `withEve`, not an eve agent schedule. `CRON_SECRET` must be a separate high-entropy server secret on the active production deployment. Environment changes need redeployment. Vercel sends it as `Authorization: Bearer …`. Family authentication, a user-agent, and deployment-protection bypass do not authorize this route. Missing/wrong credentials return 401 before database access. Success returns only `{ok:true, deletedSessions:N}`; database failure returns 503 and `{ok:false}`, without logging connection/SQL content. `Cache-Control: no-store` applies throughout. The handler keeps the shared pool open. `npm run sessions:purge` remains the one-off operator fallback.

The job deletes expired `learning_session` rows and their cascading `learning_action` and `session_image` rows, including unsaved image bytes. Explicit Portfolio copies, saved audio and brief learning notes remain. Activity access expires at a fixed maximum of 24 hours, even before deletion; reading never extends that lifetime. Vercel scheduling is best effort, can miss/duplicate runs, and does not retry failures. Inspect failures and manually run the same deployed job if needed; do not call a manual invocation native scheduling proof. Rollbacks restore old cron definitions and captured secrets, so check the schedule after every rollback/promotion.

Before recording `hourlyCleanupVerified`, on the exact deployed commit:

1. Confirm the active production cron definition and enabled schedule in Vercel; verify build output/config if registration is missing. Check unauthenticated and incorrect-secret calls return 401, including a request with valid family cookies. Missing configuration must also fail closed in local tests. Keep credentials out of output and shell history.
2. Create synthetic expired and nonexpired activities, actions and image bytes; deliberately save a Portfolio copy. Avoid session reads after expiry, because those reads also purge. Observe one real scheduled boundary, correlate its native invocation timestamp/deployment/status, then inspect direct SQL counts for the synthetic IDs. Expect expired session/action/image rows absent, nonexpired rows present, Portfolio picture/audio still readable. Repeat an authorized invocation to show harmless idempotency.
3. Retain timestamp, deployment identity, status and counts only. Remove only task-created fixtures afterward. A 404 is logical expiry evidence, not proof of physical active-table deletion.

The current Neon recovery window is 24 hours. A deleted row can remain recoverable in a historical database state for approximately another day. Hourly job delay and service failures can add time before active deletion. Neither SQL row removal nor the history setting proves immediate forensic erasure from every provider copy. Inventory snapshots, exports, historical branches and drains; do not create personal-data copies for a test. Parent-facing wording must not promise universal erasure within 24 hours. [Neon history window](https://neon.com/docs/postgres/backup-restore/history-window) documents the recovery mechanism; [Vercel Cron management](https://vercel.com/docs/schedules/cron-jobs/manage-cron-jobs) documents scheduler limits.

## Account repair and allowance recovery

The ledger intentionally keeps uncertain reservations. Retrying is a separately reserved operation; a provider outage never implies a zero-cost call. A provider account/billing rejection sets `model_allowance.blocked_reason` and blocks later dispatch across process restarts. Fixing a key alone does not erase that block.

For an actual repair, first disable live dispatch (remove the server key and redeploy), stop pending requests and inspect the intended account. Repair only the actual account problem within authorized funding. Verify the grant, supported endpoints, retention, exclusive consumption and absence of paid fallback again. Match authoritative provider request/response IDs and usage to the existing ledger; preserve every settled charge, unresolved reservation and pending liability. If a request outcome cannot be proven, keep its full hold. Do not delete rows, invent zero-cost outcomes, reset the allocation, or change `windowId` to bypass exhaustion.

If the same valid grant window, allocation and pricing policy remain in force, restore the original funding identity fields, refresh only actual check/evidence timestamps as needed, and clear the _specific reviewed account block_ under a database transaction using bound values:

```sql
BEGIN;
SELECT id, policy_identity, allocation_nano_usd, blocked_reason
FROM model_allowance WHERE id = $1 FOR UPDATE;
-- Confirm this is the reviewed window and expected prior rejection.
UPDATE model_allowance SET blocked_reason = NULL
WHERE id = $1 AND blocked_reason = $2;
COMMIT;
```

Execute through a private parameterized database client with reviewed values; `$1` is the existing fully qualified window ID, `$2` its observed rejection reason. This does not release holds or increase allowance. Reapply the repaired key only after reconciliation, redeploy, and check readiness plus totals before a permitted synthetic request. Remaining allowance may still be too small. Unknown liabilities stay held unless authoritative usage establishes settlement. `funding_changed` instead indicates identity mismatch: restore the original funding identity, or complete a separately reviewed reconciliation. Do not merely overwrite `policy_identity`. A genuinely new grant may receive its real new window ID only after account review reconciles carryover and establishes its own available allocation. No automatic reset/rollover or recurring parent chore is implemented.

## Restore and telemetry safeguards

Before any restore, revoke live access and stop/revoke its production deployment's chargeable routes. Preserve current billing evidence separately without learner content. Restore into an isolated database; purge already-expired sessions before exposing any restored database to the app. Reconcile the restored ledger against the latest ledger/provider usage and pending/unknown liabilities. Restoring old counters must never recreate spent allowance. Keep live requests disabled until the funding allocation and every outstanding reservation are accounted for; if evidence is unavailable, remain closed. Recheck cron definitions, secrets, TTL/recovery configuration, ownership and saved assets before reopening. A documented procedure is not a performed restore drill.

The application emits no learner-content logs by design; eve input/output traces and workflow payload retention are disabled. Platform tracing, runtime logs, Agent Runs and external drains are separate controls. The existing project has continuous trace sampling disabled, which does not erase historical traces or disable every manual trace/drain. Inspect all enabled destinations with unique synthetic markers through text/image/speech/research and saved-media routes; record what was actually inspected. Do not print request bodies, model instructions, media bytes, cookies or secrets during verification. Retain operational timestamps/status/counts. No provider approval is inferred from these application controls.
